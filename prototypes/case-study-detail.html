Case Study

Kredim Checkout: cutting drop-off in the merchant payment flow

Role
Lead Frontend Engineer
Timeline
2023 - 2024
Stack
next.js typescript a/b test

Problem

The merchant checkout was a single monolithic form handling every payment method, region, and merchant tier through nested conditionals. Adding a new payment method meant touching a form that already had a measurable abandonment problem, and no one wanted to be the one who made it worse.

Architecture

Split the checkout into a small state machine driving independently testable step components, with payment-method-specific logic isolated behind a shared interface. New methods became additive instead of invasive - each one implements the interface and registers itself, rather than adding another branch to a form that already had too many.

// each payment method implements the same shape
interface PaymentMethod {
  id: string;
  steps: CheckoutStep[];
  validate(state: CheckoutState): ValidationResult;
}

Decisions

Ran the rebuild behind a feature flag with a real A/B split against the legacy flow rather than a big-bang cutover, so regressions in conversion would show up before full rollout, not after. Kept the new flow in TypeScript with strict mode from day one, since the old form's biggest source of bugs was silent type mismatches between the payment gateway response and the UI state.

checkout flow diagram - placeholder

Outcome

Rolled out to 100% of merchant traffic after the A/B test confirmed the new flow held conversion and cut mid-flow abandonment.
